> [!TLDR]
> Fourteen requests, one structural cause under six of them: **every module is a
> modal `.sheet` on a single `Window`, and one 2,316-line `AppModel` owns all of
> their state.**
>
> - A sheet is mutually exclusive *by construction*. "Opening a module shouldn't close the previous one" is not a preference the current structure can express — it has to be rebuilt, not configured.
> - Four decisions taken: **tabs in one window**, **free-form drag-to-dock**, **spine first**, **Services plus a Finder extension**. Two of those are the expensive options; their cost is stated below rather than discovered later.
> - Six requests are blocked on the spine, seven are independent of it and can land in any order, and one — a report before every modification, re-checked at the moment of action — is **already built**, with one deliberate exception to settle.
> - The spine is a refactor with no visible output. It is first because everything after it gets cheaper, and because doing it later means doing parts of it twice.

This is a **plan**, not a specification. It says what order the work goes in and
why that order and not another; it does not say what the screens look like.

## Why the order is forced {#why}

Reading the request list, the natural instinct is to start with the visible
things — the icons, the popup that wastes space, the views that should combine.
The structure says otherwise.

```mermaid
flowchart TB
  subgraph now["today"]
    direction TB
    W["one Window"] --> CV["ContentView"]
    CV --> S1[".sheet: free up space"]
    CV --> S2[".sheet: compare"]
    CV --> S3[".sheet: what changed"]
    CV --> S4[".sheet: find"]
    CV --> S5[".sheet: review before trash"]
    AM["AppModel · 2,316 lines<br/>owns every module's state"] -.->|"drives all of them"| CV
  end
  classDef sheet fill:var(--series-4-soft),stroke:var(--series-4),color:var(--text)
  classDef core fill:var(--series-1-soft),stroke:var(--series-1),color:var(--text)
  class S1,S2,S3,S4,S5 sheet
  class AM,W,CV core
```

*Every module hangs off one view as a modal sheet. The red boxes cannot coexist:
presenting one dismisses another, and none of them survives being navigated
away from.*

Two consequences, and they are the ones in the request list:

1. **A sheet is modal.** It cannot stay open while you work elsewhere, it cannot
   be docked beside something, and it is sized by the presenter rather than by
   the content — which is exactly the "restricted width and height" complaint
   about *Yer açma*. Making that screen bigger inside a sheet treats the
   symptom.
2. **One object owns everything.** `AppModel` holds the scan, the tree
   navigation, the compare state, the cleanup suggestions, the search, the
   review selection and the undo stack. Two modules cannot be open at once
   partly because there is only one of each field. A second compare would
   overwrite the first.

So: three of the fourteen requests describe the *same* change from different
angles, and a fourth (realtime everywhere) is a property that only becomes
achievable once each module owns its own observation of the tree.

## The spine {#spine}

Three steps, in order. Each is separately shippable and separately green.

```mermaid
flowchart LR
  A["1 · split the state"] --> B["2 · tabs replace sheets"] --> C["3 · dockable panes"]
  A -.->|"unblocks"| A1["modules survive<br/>being left"]
  A -.->|"unblocks"| A2["realtime per module"]
  B -.->|"unblocks"| B1["modules without a scan"]
  B -.->|"unblocks"| B2["one-click handoff<br/>between modules"]
  C -.->|"unblocks"| C1["views combined,<br/>not alternatives"]
  classDef step fill:var(--series-1-soft),stroke:var(--series-1),color:var(--text)
  classDef win fill:var(--series-3-soft),stroke:var(--series-3),color:var(--text)
  class A,B,C step
  class A1,A2,B1,B2,C1 win
```

### 1 — Split the state

`AppModel` becomes a shell that owns the open tabs and the chrome. Underneath
it:

| New owner | Takes | From today's sections |
|---|---|---|
| `ScanSession` | the tree, stats, volume, phase, scan targets, exclusions, the undo stack | *Doing nothing while nobody is looking*, *Naming a root*, *Scan targets*, *Scanning* |
| `MapModule` | current directory, rows, breadcrumb, back/forward, selection, panel and visualization choice, layout caches | *Navigation*, *Treemap layout* |
| `DuplicatesModule` | match groups, folder matches, the tick selection | *Choosing things to remove* |
| `CompareModule` | both sides, the diff tree, filters, direction, plan preview, content check | *Comparing two folders*, *Deep verification*, *Which decisions are in* |
| `SearchModule` | query, results, filters | *Finding one thing* |
| `SpaceModule` | suggestions, thresholds | *Where the easy space is* |
| `ChangesModule` | the digest and the comparison against it | *What changed since last time* |

This is mechanical, and the file is already sectioned along these lines — the
`// MARK:` boundaries map almost exactly onto the table. It is done one
extraction at a time, each leaving the 298 tests green, because six test files
build an `AppModel` directly and will fail loudly on anything that moves
underneath them.

**The point of the step:** a module's state stops being a single global. A
second comparison becomes a second `CompareModule`, not a conflict.

### 2 — Tabs replace sheets

One window, a tab bar, a tab per open module. A shared `ScanSession` feeds all
of them; a module that does not need a scan does not ask for one.

That last clause is the request about modules being first-class. Concretely:

- **Compare** needs no scan at all — it walks the two folders it is given. It
  should open from a cold launch.
- **Search** needs an index, so it needs a scan. It stays honest about that:
  offer to scan rather than refuse.
- **Duplicates** and **free space** need a scan of the subtree in question, not
  necessarily of a whole disk.

**Handoff falls out of this.** "Compare the two folders this report identified"
becomes: open a `CompareModule` with both sides pre-filled, add a tab, switch to
it. Today there is nowhere for that tab to go.

**Realtime falls out of step 1 plus this.** Each module observes the
`ScanSession`'s live tree rather than reading a snapshot taken when its sheet
was presented. The tree already publishes changes — the eighth review pass was
about exactly that machinery, and the change counter is now reliable enough to
drive it.

### 3 — Dockable panes

Inside a tab, the views become panes rather than alternatives. The four table
views (*İçerik*, *En büyük*, *Türler*, *Kopyalar*) and the three visualizations
(*Alan haritası*, *Halka grafik*, *Katman grafik*) stop being two radio groups
and become seven things you can show together.

> [!WARNING]
> **This is the expensive choice, and it is worth being explicit about why.**
> SwiftUI has no docking. Free-form drag-to-dock means hand-building: a layout
> tree that can be split and rebalanced, drop-zone hit-testing with live
> previews, drag handles that do not fight the scroll views inside each pane,
> and persistence of the whole arrangement across launches. There is no
> half-built version that feels acceptable — a docking system that is 80% right
> reads as broken, because the 20% is exactly the part you touch.
>
> Estimate: this is the single largest item on the list, larger than the state
> split. The mitigation is to build it behind the same pane protocol that a
> preset layout would use, so the panes are usable while the dragging is still
> being made good.

## What rides on the spine {#rides}

| Request | Needs | Note |
|---|---|---|
| *Yer açma* as a screen, not a popup | steps 1–2 | Becomes a tab. The width problem disappears rather than being tuned. |
| One-click compare from the identified folders | steps 1–2 | A button that opens a pre-filled compare tab. |
| Opening a module doesn't close the previous | steps 1–2 | This *is* step 2. |
| All views update in realtime | step 1 | Each module observes the live tree instead of a snapshot. |
| Views combinable, dockable layout | step 3 | |
| Modules as first-class, usable without a scan | steps 1–2 | Compare is the proof case: it genuinely needs nothing. |

## What does not {#independent}

These are independent of the spine and of each other. Rough size, not a
schedule.

| Request | Size | What it actually is |
|---|---|---|
| Icons that mean something (*start over* looks like zoom in) | hours | An audit of every SF Symbol in the app against what the control does. `arrow.counterclockwise` for start over, not a magnifier. |
| Confirm before a long operation that loses state | hours | A rescan discards the tree, the undo stack and every open module. One sheet, reused. |
| Folders unselectable in the picker, like disks | hours | The picker already has the concept for disks; manually added folders bypass it. |
| Drag and drop where applicable | days | Compare's two wells first, then the scan-target picker. `.dropDestination` per surface, no shared machinery needed. |
| Fuzzy search | days | Today's search is substring with an ASCII fast path. Fuzzy means subsequence matching plus a ranking function — exact first, then prefix, then subsequence by gap size. Self-contained in `Find.swift`. |
| More filters (type, date, size, content) | days | Type, date and size are already in the store. "Content-specific" is not, and is a separate question — see below. |
| Flat table of everything with all columns | days | The store is already columnar; this is the view that matches its shape most directly. Sortable by any column, virtualised. |
| Finder Services entry | hours | `NSServices` in the Info.plist the build script already generates and signs. |
| Finder extension for the top-level menu | days, plus packaging | See the warning below. |
| Headless / CLI | days | Partly built: `Sources/diskmap` exists. Needs the modules exposed as subcommands with machine-readable output. |

> [!WARNING]
> **The Finder extension is a packaging change, not a feature.** A top-level
> right-click item needs a Finder Sync app extension: its own bundle
> identifier, its own entitlement, its own signing, and an `.appex` embedded in
> the host app. This repository is a Swift package built by a shell script — it
> has no Xcode project, and SwiftPM cannot produce an appex. Taking this option
> means either adding an Xcode project alongside `Package.swift` or hand-rolling
> the appex bundle in the build script.
>
> The Services entry works today with no packaging change and delivers most of
> the value. Recommendation is to ship that first and treat the extension as its
> own piece of work, so the packaging change is not on the critical path of
> anything else.

## The one already built {#already}

> Every modification operation should show a report before taking the action,
> and we should have checks in place just before taking the action.

This is the subject of the safety review and it is in place. Every destructive
path builds an explicit plan, shows it, and re-checks each target's kind, size
and date at the moment of the click — refusing the step if the disk moved
underneath the plan. That was findings 4 and 23; the gate diagram in
[the review](#f/docs/sync-safety-review-2026-09-02.md) shows where each check
sits.

**One deliberate exception, now in conflict with the rule as stated.** A file
under 5 GB trashed from a context menu goes straight to the Trash with no
report — the reasoning written at the time was that it is recoverable and
undoable. Your sentence says every modification shows a report. Taking the
sentence literally is a small change and I will make it that way unless you say
otherwise; the cost is a confirmation on every single-file delete, which is the
kind of friction that trains people to click through without reading.

## Order {#order}

```mermaid

  P0["now"] --> P1["state split<br/>7 extractions"]
  P1 --> P2["tabs"]
  P2 --> P3["realtime<br/>per module"]
  P3 --> P4["docking"]
  P0 -.->|"any time, independent"| Q["icons · confirm · picker<br/>Services · drag-drop<br/>fuzzy · filters · flat table"]
  P2 -.->|"after tabs exist"| R["compare handoff<br/>modules without a scan"]
  P4 -.->|"last, own packaging track"| S["Finder extension · CLI"]
  classDef spine fill:var(--series-1-soft),stroke:var(--series-1),color:var(--text)
  classDef side fill:var(--series-2-soft),stroke:var(--series-2),color:var(--text)
  class P1,P2,P3,P4 spine
  class Q,R,S side
```

The independent column is deliberately parallel: it is where to go when the
spine hits something that needs thinking about, and none of it is wasted by the
restructuring.

## What could go wrong {#risks}

- **The state split touches everything and shows nothing.** The mitigation is
  that it is seven separate extractions, each green, each committed — not one
  landing. If it stalls halfway the app still works.
- **Six test files construct `AppModel` directly.** That is protection, not a
  problem: anything that moves breaks a test rather than a user. Those tests get
  updated with each extraction rather than at the end.
- **Docking is where this could turn into a swamp.** It is last on purpose. If
  it turns out worse than estimated, the panes still exist and a preset split is
  a day's work on top of them.
- **Tabs plus realtime multiplies observation.** Five open modules all watching
  one live tree is five recomputations per event. The debounce and the change
  counter already exist; what does not exist yet is per-module throttling, and
  it will be needed before five tabs are comfortable.

## Left open {#open}

- **"Content-specific properties" in filters** — this could mean the file kind
  the app already derives, or reading inside files (EXIF dates, media duration,
  archive contents). The second is a different kind of feature: it needs opening
  every file, which is the one thing the scanner is built to avoid. Worth
  pinning down before it is designed.
- **"A complete disk management tool"** — deliberately not answered here.
  Adding capabilities before the five existing ones are first-class would make
  the same mistake this plan exists to undo.
