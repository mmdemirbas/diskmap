> [!TLDR]
> The worst defect was invisible to every test and every screenshot: folder
> matching silently broke the moment a file changed on disk, reporting
> unrelated folders as identical copies.
>
> - Nine defects fixed, each with a test that fails without the fix.
> - The profile says **do not optimise our code** — a scan is 95.6% kernel and
>   verification runs at the drive's speed.
> - The app now measures itself into a local file, so the next slow scan can be
>   compared against this one instead of remembered.

## How the review was done {#method}

This was a read of the code looking for ways it could be wrong, not a test run
looking for failures — the distinction matters, because every one of the nine
defects below passed the existing 95 tests. Four files carry almost all the risk
and were read end to end: the scanner's worker loop, the live-update path, the
node store, and the two matching passes added last round.

The order of what follows is deliberate. The mechanism defect comes first
because understanding it explains three of the others; the profile comes after
the fixes because measuring code you are about to change wastes the measurement.

## The defect that mattered most {#index-order}

Folder matching hashes every node so that two folders holding the same thing
come out with the same number. Computing that requires visiting children before
parents. The original code got this for free from a property of the store: after
a scan, a child always sits at a higher array index than its parent, so a single
loop from the last index down to zero visits them in the right order.

That property is true of a fresh scan. It stops being true the first time the
filesystem changes.

```oku-diagram
{"src":"flowchart TB\n  subgraph B[\"After a fresh scan — index order works\"]\n    direction TB\n    P1[\"#5 Concerts\"] --> C1[\"#6 one.mov\"]\n    P1 --> C2[\"#7 two.mov\"]\n  end\n  subgraph A[\"After one relist — index order is inverted\"]\n    direction TB\n    P2[\"#12 Concerts (new node)\"] --> C3[\"#6 one.mov\"]\n    P2 --> C4[\"#7 two.mov\"]\n    OLD[\"#5 Concerts (marked removed)\"]\n  end\n  classDef ok fill:var(--series-2-soft),stroke:var(--series-2),color:var(--text)\n  classDef bad fill:var(--series-4-soft),stroke:var(--series-4),color:var(--text)\n  classDef gone fill:var(--surface),stroke:var(--series-5),color:var(--text)\n  class P1,C1,C2 ok\n  class P2,C3,C4 bad\n  class OLD gone","caption":"Relisting a folder appends a new node for it and re-points the untouched subtree. The children keep their old, lower indices."}
```

Relisting a folder appends a fresh row for every entry and re-points any
unchanged subtree at the new row, marking the old one removed. That is what
makes a live update cheap — the subtree is reused rather than rescanned. It also
means the new parent has a **higher** index than its own children.

Walking from the last index down then reaches `#12` before `#6` and `#7`. Their
hashes are still zero, so the folder's hash becomes a function of one thing: how
many children it has. Every reattached folder with the same number of children
hashed identically.

The consequence is worse than a missing feature. The panel does not go blank; it
fills with confident, specific claims that two unrelated folders are identical
copies, next to a number saying how much space deleting one would free.

```oku-info-tip
{"summary":"The fix, and why it is correct whatever the indices look like","content":["Pre-order has the property the index order only accidentally had: a parent is always emitted before its children. Reading that sequence backwards is therefore a valid post-order, no matter how the nodes are laid out in the arrays.",{"k":"code","src":"var order = [Int32]()\nvar stack: [Int32] = [0]\nwhile let node = stack.popLast() {\n    order.append(node)\n    if order.count > store.count { return order }   // refuse a cycle\n    for child in store.children(node) { stack.append(child) }\n}\n// then evaluate order in reverse","lang":"swift"},"It costs an extra Int32 array and non-sequential reads. Measured at 234 ms over 9.6 million nodes, which was cheap enough that keeping the old fast path behind a flag would have bought two code paths for the same computation and nothing else."]}
```

The regression test builds two folders holding completely different files,
forces a relist, and asserts they still hash differently. Against the original
code it fails with both folders reporting hash `7562127255311276876`.

## Everything else the review turned up {#defects}

Three of these come from the same place as the one above: the live-update path
is where the tree stops being the thing the scan produced.


The store-growth one deserves a sentence of its own, because it is the kind of
defect that only shows up after hours of use. Watching a folder where a build
writes output means a relist per event, and each relist appended a row for every
entry in that folder and marked the previous rows removed. Nothing reclaims
them. A day of work with the app open would have accumulated hundreds of
megabytes of dead nodes — and the symptom would have been "the app gets slow and
fat if you leave it running", which is exactly the kind of complaint that never
gets diagnosed.

## What the profile says {#profile}

The most decision-relevant number is not how long a scan takes. It is where that
time is spent.

```oku-chart
{"type":"bar","title":"CPU during one scan of a 9.6M-node home folder (seconds)","rows":[{"label":"Kernel — reading directories","value":218.15,"display":"218.15 s"},{"label":"Our code","value":10.08,"display":"10.08 s"}]}
```

95.6% of the CPU a scan burns is the kernel walking directories. Rewriting the
Swift side perfectly would move about 4% of the total. That is the finding that
decides where effort goes, and it says: not here. Wall clock was 59.2 s for
228 s of CPU, so roughly 3.9 cores were busy across the ten worker threads.

Everything the interface does on demand is far cheaper, and the shape of it is
the reason the treemap needs no work at all:

```oku-chart
{"type":"bar","title":"One panel refresh over the same tree (milliseconds)","rows":[{"label":"Folder matching, total","value":586,"display":"586 ms"},{"label":"— of which hashing all 9.6M nodes","value":234,"display":"234 ms"},{"label":"File matching","value":70,"display":"70 ms"},{"label":"Laying out a view","value":0.046,"display":"0.046 ms"}]}
```

Layout does not appear on that chart at any readable size, and that is the
point. It lays out the level being viewed, behind a byte-threshold prefilter, so
its cost follows the number of visible cells rather than the size of the tree —
0.046 ms for a 20-cell icicle, and it never once crossed the 40 ms recording
threshold even on a three-million-node tree.

Deep verification read 9.29 GB in 4.2 s, which is 2.2 GB/s. That is the drive,
not the code.

**No optimisation is warranted by this profile.** That is a conclusion, and it is
worth stating plainly rather than inventing work to look diligent. The four
performance changes made this round all came out of the correctness review — the
cache key, the in-place relist, the per-row lookup and the lock scope — not out
of the measurements.

## What the app now records about itself {#observability}

One call site, two outputs, both local.

```oku-diagram
{"src":"flowchart LR\n  CS[\"Telemetry.begin / record\\nat the call site\"] --> SP[\"os_signpost\\nfree unless recording\"]\n  CS --> JL[\"metrics.jsonl\\nApplication Support\"]\n  SP --> INST[\"Instruments\\nstage next to kernel time\"]\n  JL --> CLI[\"dmbench metrics\\ncount, p50, p95, max\"]\n  JL --> MENU[\"Scan → Show diagnostics log\"]\n  classDef src fill:var(--series-1-soft),stroke:var(--series-1),color:var(--text)\n  classDef out fill:var(--series-3-soft),stroke:var(--series-3),color:var(--text)\n  class CS src\n  class INST,CLI,MENU out","caption":"Signposts answer \"why is this slow right now\". The file answers \"was it always slow\"."}
```

Signposts are the only way to see a stage next to the kernel time around it,
which matters a great deal here given the chart above. The file is the half that
did not exist: a scan that took 50 s in September and takes 90 s in November is
a finding, and it is only a finding if the September number was written down at
the time.

A record is one line, and this is a real one:

```json
{"t":"2026-09-01T05:44:47.032Z","v":1,"s":"3afd47553578","e":"scan","cancelled":false,"dataless":1433020,"dirs":1605851,"files":7984581,"footprint":490228672,"hardlinks":31350,"logical":15242782991880,"ms":49596.848,"nodes":9632749,"physical":6726080335872,"roots":1,"threads":10,"unreadable":0}
```

**No path and no file name ever reaches a record.** This is a disk analyzer; its
own log would otherwise be a listing of everything you own. That is not a
convention to remember — a test walks every `Telemetry.record` and `span.end`
call site in the source and fails if one passes a path or a name.

Three more decisions worth knowing:

- **High-frequency stages only reach the file when they were slow.** A layout
  relaid on every resize frame would otherwise bury a month of real events. The
  signpost still fires every time. `DISKMAP_METRICS_ALL=1` drops the thresholds,
  which is how you confirm a stage that is never slow is instrumented at all —
  without it there is no evidence either way, which is its own kind of blind
  spot.
- **Recording is off inside tests.** The environment variable alone was not
  enough; a hundred tests scanning temporary directories had already buried the
  real history once. Asking whether XCTest is loaded answers it directly.
- **It rotates at 8 MB and keeps two files.** The whole footprint is bounded and
  local. Nothing here opens a network connection, and `DISKMAP_METRICS=0` turns
  it off entirely.

It has already earned its place. Three of the four scans above recorded zero
unreadable directories and one recorded three — a transient a single run would
have shown as either "fine" or "a problem", with no way to tell which.

## Questions you might have next {#faq}

**Would any of these have shown up in normal use?** The hash defect, certainly —
it needs only one file to change anywhere in the tree while the app is open,
which is to say it needed the app to be used for more than a minute. The store
growth needs a few hours. The trash-a-stale-node one needs a confirmation sheet
left open while something else deletes the file, which is rare but silent when
it happens.

**Why did 95 passing tests not catch the hash defect?** Every test scanned a
temporary directory and immediately asserted. None of them changed a file and
relisted first, so none ever produced a store where the index invariant was
broken. The new tests do exactly that, and it is worth noting that the fix and
the test were written from reading the code, not from a failure.

**How do I read the accumulated metrics?** `dmbench metrics` prints count, p50,
p95 and max per stage, then recent full scans with throughput and memory, then a
count of problems. Percentiles over four samples mean very little; the count
column is there so you can see when they start meaning something.

**What would make the scan faster?** Not our code. The remaining levers are
fewer entries to read — a persisted snapshot so a rescan only visits what
changed — or a different traversal API, and neither is a small change. That is a
design question for a later round, not an optimisation.
