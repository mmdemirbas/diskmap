## What was the complaint, and what did the app say about itself?

The report was "it is using too much battery". `ps` agreed: the installed
app sat at **146.3% CPU** after forty minutes, and its cumulative CPU time
tracked about 70% of wall clock for the whole session.

Guessing at that point would have been cheap and wrong. The telemetry added
in the previous round had been running the whole time, so the first move was
to read it rather than to start optimising. Across 43,211 records from ten
runs:

| stage | count | p50 | p95 | max |
|---|---|---|---|---|
| `live.flush` | 4,008 | 471 ms | 4,798 ms | 74,261 ms |
| `scan` | 28,383 | 25.9 ms | 88.0 ms | 68,708 ms |
| `live.relist` | 3,574 | — | — | — |
| `live.resize` | 6,800 | — | — | — |
| `layout` | 371 | 119 ms | 498 ms | 2,062 ms |

Narrowed to the session that was still running — 41 minutes, 19,259
records — the shape of the problem was already visible:

- **1,966 seconds of flush inside 2,736 seconds of wall clock: a 72% duty
  cycle.** The app was doing filesystem work nearly three-quarters of the
  time, indefinitely.
- **14,767 nested scans costing 457 seconds**, for 993,536 nodes in total.
- The store had grown from 9.6M nodes at scan time to **30.0M**, and the
  cost of a single relist rose about 50% across the session as it did.

One reading in that data was mine and wrong: the largest `scan` record,
11,599,813 nodes, is the launch scan, not a runaway rescan. Excluding it,
the 14,731 remaining scans averaged **about ten nodes each and roughly
30 ms apiece**. That ratio — thirty milliseconds to read ten nodes — is
what pointed at the first cause.

## Why did reading an empty folder cost 30 milliseconds?

A live update relists one directory. Any subdirectory in it that the tree
has not seen before gets scanned, and the scanner sizes its arrays from the
volume's used-inode count:

```swift
let estimate = normalized.roots.reduce(0) { $0 + usedInodeCount($1) }
let capacity = estimate > 0 ? min(Int(Double(estimate) * 1.05) + 1024, 80_000_000) : 1 << 20
store.reserve(capacity)
store.beginInterning(expectedNodes: capacity)
```

`statfs` answers for the **volume**, whatever path it is handed. So a
folder that had just appeared — nearly always empty, because a build or a
package manager creates a directory before filling it — reserved room for
**12.2 million nodes**: some 620 MB across the nine arrays plus a 134 MB
intern table, and twelve worker threads. Several times a second.

`ScanOptions.expectedNodes` lets a caller that knows better say so. A
relist asks for 4,096 nodes and two threads. `dmbench relistcost` measures
the difference and is kept so the figure can be re-checked:

```
directory with 8 entries, volume using 11,927,398 inodes
  sized from the volume     12.411 ms   9 nodes   peak footprint +1.6 MB
  sized by the caller        0.084 ms   9 nodes   peak footprint +508 KB
```

**148× on the dominant per-event cost.** Worth stating precisely what that
is and is not: the peak *resident* footprint barely moves, because reserved
pages are not touched. The 620 MB is address space, so what was actually
being paid was the kernel's work mapping and unmapping it — which is why it
showed up as CPU rather than as memory.

## What was left after that, and where was it?

Measured on the real home directory over 180 seconds, the fix took the
watching cost from 23.8% of a core to 15.0%. Better, and still too much for
an app that is only sitting there.

Rather than guess again, `dmbench churn` watches without maintaining a tree,
so the measurement does not pay the cost it is measuring. It reports which
directories the filesystem is actually changing, and how many entries each
one holds:

```
  9238 events across 447 directories

  events   entries  directory
    1866     1.016  ~/.claude/context-mode/sessions
    1567    78.995  ~/Library/Caches/.../Brave-Browser/Default/Cache/Cache_Data
     785     7.542  ~/Library/Caches/.../Brave-Browser/Default/Code Cache/js
     415       159  ~/dev/mmdemirbas/ajans/build/client/_app/immutable/chunks
```

**One directory dominated everything else put together.** A browser cache
holding 78,995 entries produced 1,567 events in two minutes. Every relist of
it walks all 78,995 and appends that many rows — which is also where the
store growth came from. Applied event by event, that one folder is 63
million appended rows a minute, from a directory nobody has ever opened in
this app.

Each directory is now held off ten times what its last relist cost, capped
at 30 seconds. An expensive folder settles into its own duty cycle; a small
one beside it stays immediate. The hold-off is a delay and never a refusal:
the directory stays queued and the flush returns when its wait expires,
rather than spinning on the debounce.

## What else was on the same path?

Three smaller cuts, and one correctness bug found while looking.

**The debounce was a constant.** A fixed 0.35 s means a machine doing steady
work stays busy permanently: the flush costs what it costs, and the next one
is queued a third of a second later regardless. The wait now follows what
the last flush actually cost — clamped to [0.35 s, 8 s] — so no constant has
to guess how fast a particular machine writes.

**Nothing was gated on being visible.** Live updates now drop to a 30-second
cadence when no window is on screen, and row rebuilds and treemap layouts are
deferred until one is. The tree keeps following the filesystem either way;
only the rate changes, and coming back to a stale window is the one failure
this app must not have. Occlusion state is the right signal rather than
activation: a window can be entirely covered while the app is still
frontmost, and readable beside the editor being typed in.

**The instrumentation was charging the thing it measured.** A record per
relist and per resize is a disk write per filesystem event, roughly one every
0.3 s. Those became counters folded into the flush record, and a subtree scan
is only worth a line if it was slow.

**An unopenable folder was being treated as a deleted one.** Every failure of
`open()` on a directory dropped its bytes out of every total above it and
zeroed its children. Only `ENOENT`, `ENOTDIR` and `ELOOP` mean that. Running
out of descriptors, an interrupted call, or a permission just revoked are all
temporary — and the damage lands twice, because a folder left with no known
children makes the next event on it rescan the whole subtree from scratch.
The regression test fails four ways against the old code.

## What does it cost now?

Watching the same real home directory for 180 seconds, same machine, three
builds:

| | before | scan fix | and hold-off |
|---|---|---|---|
| CPU, share of one core | 23.8% | 15.0% | **7.6%** |
| store growth in 180 s | +1.98M nodes (77 MB) | +1.03M (40 MB) | **+261k (10.2 MB)** |
| tree changes applied | 288 | 204 | 161 |
| UI notifications | 167 | 92 | **61** |
| debounce it settled on | 0.35 s fixed | 2.76 s | 0.35 s |

**3.1× less CPU and 7.6× less store growth.** The debounce returning to its
floor in the third column is the adaptive mechanism working rather than
failing: it backs off only while flushes are expensive, and they no longer
are.

Scope of these figures: `dmbench live` exercises the tree, not the window, so
the visibility gating is not in them — an app sitting in the background gains
on top of this. Machine write activity varies between runs, which is why the
three columns were measured back to back on the same tree rather than quoted
from different sessions.

## What is still true and not fixed

**The store still grows.** Every relist whose entry names changed appends a
new child block and abandons the old one; nothing reclaims it. At 10.2 MB per
three minutes that is roughly 200 MB an hour, down from about 1.5 GB, but it
is a slope rather than a ceiling.

The fix would be compacting the arrays and remapping every index. That was
considered and deliberately not done: the UI holds node indices in the
selection, the expanded set, and the tick list that feeds the Trash. A remap
bug there would not show up as a crash — it would show up as the wrong file
being moved to the Trash, which is the one failure this app cannot have. If
growth needs to be bounded, the safe instrument is a rescan, which already
resets those references visibly.

**FSEvents still wakes the process at its 0.4 s latency** even while
suspended; only the expensive work is deferred. Raising the stream latency
while hidden would need the stream torn down and recreated from the last
event ID to avoid losing changes, which is real complexity for a
second-order gain.
